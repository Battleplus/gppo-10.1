## 为什么过去多次停在修复

历史修复横跨包身份、依赖、跨系统入口、数据语义与资源计量。静态测试、预检或底层替身测试并不覆盖全部正式路径，因此曾反复在尚未实际走过的接口失败。

| 问题组 | 历史实际问题 | 对结果的影响 |
|---|---|---|
| 冻结身份/授权 | 缺 manifest 摘要字段、文件尾空行改变哈希、旧 attempt 硬编码、授权 JSON 尾随字符 | 大多在环境/模型前停止；不是研究负结果 |
| 运行时/依赖 | WSL 系统 Python 无 torch、漏 production_policy、远端 CUDA 库不匹配、隔离模式包路径设置过晚 | 模型没启动，不能报告 loss 或效用 |
| 远端工程 smoke | SFTP 排他模式上传产生空授权文件、测试引用历史绝对路径、Unix socket 路径过长 | smoke 多次失败；后来本机 GPU 完成连通性验证 |
| 数据合同 | completion 模式记录不一致、生命周期未导出、首步效用被误当完整续行、unknown 语义不清 | 需要新标签合同和新采集，不能仅靠训练修补 |
| CPU/结算 | 同阶段基线不同步、短命子进程与退出尾段、嵌套 CPU 重复计量风险 | 工程/资源状态与科学结果必须分开 |
| 训练吞吐与阶段 wall | 3,600s 未完成九路线，旧账本扫描存在额外开销但归因不完整 | 七路复用、8302 重训、8303 首训，后来完成任务评价 |

“修好了入口”只代表那项工程条件改善。最新实验已经越过这些启动障碍并得到正式任务负结果，接下来应聚焦研究机制，而非把所有结论再次推迟到工程准备。

## 历史保留规则

原始报告中的 `technical_stop`、`prediction_gate_stop`、旧 pending 和失败导出原样保留。不同模式、不同数据合同、不同 attempt 不合并成一次成功运行。工程 smoke、真实模拟器研究、离线复算三种证据分开；本机运行成功不替代远端未完成的验收。
