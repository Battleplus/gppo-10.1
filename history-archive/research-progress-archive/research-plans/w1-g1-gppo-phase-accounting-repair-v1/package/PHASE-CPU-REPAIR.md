## 修复原因

旧 worker 初次选择 staging 时，本地同阶段快照将 CPU 起点从0推进到2.866153s，
但未发送握手。supervisor 仍记0；进入训练前严格连续性检查拒绝。这不是噪声，
不是预算超限，也不是 GPPO 或世界模型机制失败。
旧 supervisor 立即清理 worker，导致异常结算未落盘；status 留在 initializing。

## 状态与计量原则

阶段起点、进度采样点、最后双方确认的转换分别记录，不混用。
初次阶段进入确认从 CPU0 起的 worker 生命周期，保留 supervisor staging 原起点，
包括 Python 启动和既有暂存offset；不得从首次采样减掉已消耗CPU。
同阶段快照是自阶段起点至当前的累计观察，不是新的阶段消耗，不能把连续累计值相加。
真实阶段转换经过序列与载荷身份校验及确认后推进；重复消息同序列同载荷幂等，
同序列不同载荷拒绝。确认丢失或超时保留未确认状态，停机，不继续下一研究阶段。
阶段累计只加已提交的非重叠区间；未关闭阶段和退出尾段以独立分项核对最终总量。
server已提交的阶段与worker已收到确认并落盘的阶段分别记录；最终确认丢失时，
二者可能不同，此时剩余CPU总量仍实测，但阶段归属保持null并停止，不冒充双方确认。
正常退出也核对开放阶段尾段和阶段上限；逆序测量、未知终止阶段不得判定资源通过。

CPU总量以外层 kernel waited CHILDREN 及其SELF实测为各自范围依据，内部supervisor、
worker和阶段行是嵌套分解，不能在外层总量上再次相加。短子进程使用waited CPU，
不依赖轮询抓到它。没有委托cgroup时CPU限制仍是采样／退出结算，不称硬限制。
Windows/WSL桥与正式控制器最后写入／退出的历史计量缺口不由本次局部测试消除。

## 异常保留

worker 在任何可能再次失败的结算前写首次 traceback、调用状态、最后确认阶段。
协议失败的异常结算不再次切阶段握手；保存不完整信息，不覆盖首次错误。
supervisor 允许有界错误落盘机会并维持预算检查，随后只清理自有进程。
worker结算缺失时外层保存明确的不完整结算，未知账本值是null，不是零。
原始stderr与协议请求／确认／拒绝记录及SQLite共同导出，身份验证后才记导出通过。

## 工程测试边界

最终源码运行本机Ubuntu-24.04冻结Python3.11.16，CPU0、单线程、CUDA不可见、-I -B。
生产worker/runner完整核验fixture包、环境输入与模型文件摘要，只读取字节身份。
包外trace在生产训练函数第一条语句之前停止；它用于验证首次训练阶段握手，
绝不声称训练、采集或完整任务矩阵已执行。控制性异常是该工程用例预定义终点。
系统测试实际运行AF_UNIX、SO_PEERCRED、子进程、wait、SQLite、文件落盘和导出；
故障注入只用于CPU工作量、socket消息及退出边界，不跳过身份、基线或预算断言。
最终包外证据分别记：协议回归、生产首转换回放、退出CPU核对、跨系统只读预检。
以真实路径、确认阶段、无重复/遗漏计量和异常证据判断，不以测试总数替代验收。
