# Independent CPU Scope Review

Review target: `research-plans/w1-task-outcome-g1-g2-joint-production-acceptance-v2`, with emphasis on `linux_process_scope.py`, `supervise.py`, `metered_joint_entry.py`, `joint_remote_native.py`, `launch_joint_once.py`, and their accounting contracts. This is a source review; it does not authorize or claim a formal/remote attempt.

## Conclusion

The normal successful path has a coherent lifetime settlement design. Linux `/proc` snapshots include each live process's `utime+stime` and kernel-waited `cutime+cstime`; subreaper cleanup catches new adopted descendants; final `RUSAGE_SELF`/`RUSAGE_CHILDREN` and the outer parent's waited-child lifetime close the accounting after the inner snapshot. Nested snapshots are diagnostic and are not added again. A real short-lived child fixture burns CPU after printing its own snapshot, and the parent's `wait4`-backed lifetime delta captures that tail.

That conclusion is about **eventual accounting on the normal path**, not immediate CPU-cap enforcement. The implementation states `cpu_scope_hard_enforcement=false`; without a delegated cgroup, supervisor cap checks are sampled. Nor is final status persistence guaranteed if closeout is killed or blocked in kernel I/O. The exception/timeout path explicitly emits incomplete accounting where it reaches its failure writer, but it can block before that writer and can leave registration without a terminal event. Do not present this as a hard CPU limit or guaranteed terminal settlement.

## Lifetime Settlement

- `linux_process_scope.py:72-86,117-175,178-203` parses self and waited ticks, takes owner/starttime-checked descendant snapshots, rejects unstable identity/tree changes, and sums self plus waited ticks. A reaped child is represented in its living parent's waited counters instead of being added twice.
- `linux_process_scope.py:234-272,309-355` enables and verifies subreaper mode, snapshots the pre-existing direct-child identities, then signals/reaps only post-baseline adopted descendants after checking PID, UID, and starttime. An unstable scan or unresolved live descendant raises an error rather than reporting successful cleanup.
- `supervise.py:174-176,201-209,228-260` enables subreaping before spawning the worker, polls a stable tree, and in `finally` stops the worker, cleans adopted descendants, then reads final `RUSAGE_SELF` and `RUSAGE_CHILDREN`. Its final status only reports lifetime settlement complete when subreaping was enabled and no failure occurred. The serialized scope still correctly says it is not complete/hard-enforced at the broader wrapper level.
- `metered_joint_entry.py:133-160` enables its own subreaper before starting `joint_remote_native.py`, waits for the child, reaps newly adopted descendants, and computes `waited_cpu` as the `RUSAGE_CHILDREN` delta from a pre-launch baseline. `closure_accounting()` at lines 30-68 charges that waited lifetime once, adds disjoint parent self CPU and an explicit closing reserve, and uses the inner snapshot only to calculate a tail diagnostic. The tail is folded into settlement allowance, not added a second time to total CPU.
- `joint_remote_native.py:383-415` now updates the native total and settlement CPU/wall values from the same post-write snapshot; a later final write/exit tail remains measured by the outer wait. This keeps the known inner closeout writes in settlement attribution while preserving the rule that the waited lifetime, rather than nested snapshots, is charged once.
- `test_metered_joint_entry.py::test_real_wait_captures_cpu_after_child_final_snapshot` exercises a real short-lived process that burns about 0.08 CPU seconds after printing its snapshot. The outer waited lifetime recovers at least 0.07 seconds of tail and the total is charged once. The recorded WSL test run passed all five tests in this module (`real-exit-tail.json` / `.stderr`, exit code 0, no SSH or formal attempt).

The coverage above assumes the child has actually been waited and the owned descendants have actually been reaped. It does not turn a live-process snapshot into an atomic kernel snapshot: `supervise.py` explicitly records `/proc` non-atomicity and fails closed on unstable/nonmonotonic observations. Stage handshakes (`phase_handshake.py:66-149`) authenticate the worker and take a boundary snapshot only when no descendant processes are present; they are synchronous accounting boundaries, not kernel-enforced execution barriers or proof that CPU use stops at that instant.

## Enforcement Is Sampled

`supervise.py:201-225` samples the tree, runs `guard()`, writes status, and sleeps for `sample_interval` (default 0.5 seconds). `guard()` (`supervise.py:129-138`) detects a cap crossing only at a check. There is no delegated cgroup CPU controller in this package; state and the final evidence explicitly set `cpu_scope_hard_enforcement=false` and say enforcement is sampled. Work can therefore cross a cap between checks before the supervisor requests shutdown. Final `RUSAGE` settlement rejects an observed total overrun, but that is retrospective rejection, not an immediate kernel ceiling.

The stage handshake can attribute/synchronize a reported stage boundary within its stated scope, but it does not make the whole run hard-real-time. Acceptance text should preserve this distinction: **lifetime settlement can include completed short-lived work and post-snapshot tail; sampled enforcement can still overshoot before detection.**

## Exception and Timeout Paths

The ordinary inner failure route in `joint_remote_native.py:433-465` tries to stop its child, records `technical_stop`/`final_resource_pass=false`, writes failure settlement, and avoids automatic retry. The outer entry now uses bounded child waits, preserves cleanup errors, and writes a fail-closed lower-bound record (`metered_joint_entry.py:178-207`): total CPU is null, stage attribution and accounting are incomplete, and final resource pass is false if complete lifetime cannot be established. This is the correct treatment of unresolved descendants.

The failure route is more explicit now, but it still cannot guarantee closeout in all kernel states:

- On timeout, `metered_joint_entry.py:145-151` kills the child and bounds the follow-up wait to two seconds; the exception route at lines 178-189 repeats a bounded wait and preserves timeout/cleanup errors. A process stuck in uninterruptible kernel I/O can outlive those waits. The code can record that as unresolved only if it proceeds to the failure writer; this is not proof that the process has exited or that its remaining CPU is known.
- The exception path records `reaped_child_cpu_delta_lower_bound_seconds`, not a total. If descendants remain alive/unreaped, `RUSAGE_CHILDREN` does not yet contain their lifetime; the explicit null total and `accounting_complete=false` must remain authoritative.
- `joint_remote_native.py:253-265` writes a durable registration handoff immediately after REGISTERED. `metered_joint_entry.py:95-105,197-204` checks attempt, outer PID, actual child PID, manifest hash, and hashes hash before appending FAILED on an outer exception. The new unit fixture in `test_metered_joint_entry.py:84-96` checks a valid handoff plus wrong-PID and wrong-attempt rejection. This verifies the handoff parser, not an actual server ledger transition from `metered_joint_entry.main()`.
- There remains a narrow failure interval between the server's REGISTERED append and the child's handoff write. If handoff creation fails in that interval, the outer records terminal status unknown instead of claiming closure; this is fail-closed, but does not guarantee a terminal ledger event. The terminal append and durable outer-stop file are also separate operations.
- Closing CPU and wall signals are installed before the failure-path terminal append and failure-marker write (`metered_joint_entry.py:195-205`). The CPU limit uses whole-second `RLIMIT_CPU` at `floor(own_cpu)+2` while the accounting charge reserves 3 seconds; this leaves signal-granularity margin by design, but cannot prove final writes fit. The 5-second `ITIMER_REAL` handler calls `os._exit(124)`, which bypasses Python cleanup when delivered. Neither signal guarantees progress while a task is blocked in uninterruptible I/O; a signal can therefore prevent either terminal registration or outer-stop persistence.
- The normal path appends the terminal registration event before its final `durable_atomic_json()` (`metered_joint_entry.py:162-176`). A CPU/time signal or blocked/fsync failure in that interval can leave registration terminal state ahead of the final-settlement file. `durable_atomic_json()` (`infra_io.py:82-110`) fsyncs the temporary file and containing directory and retries bounded ordinary `OSError`s; it cannot make D-state I/O complete by a deadline.

The minimum fail-closed shape requested for this path is now present in `failure_accounting()` (`metered_joint_entry.py:83-92`): lower-bound CPU only, wall/child/timeout/cleanup details, null total, incomplete stage and lifetime flags, false resource pass, and unknown terminal status until verified. This should remain the policy when wait/reap, handoff, append, or final write fails; do not fill the null total from a partial RUSAGE delta or infer a stage.

The source now includes unit coverage for the handoff file's attempt/PID checks and for `failure_accounting()` with synthetic unresolved cleanup. The captured 18-test `abnormal-lifetime-handoff` stderr predates the handoff test (it lists no `test_handoff_binds_actual_inner_pid_and_packet_identity`), so it is not evidence that the new test passed; the root agent is running the final affected tests. Neither the test source nor captured run exercises a controlled `metered_joint_entry.main()` timeout/exception through a real process, an actual FAILED server-ledger append, D-state I/O, or interrupted fsync. Preserve those test and runtime limits in the review.

The inner worker cleanup also remains unbounded after its forced kill: `joint_remote_native.py:433-440` calls `child.kill()` and then `child.wait()` without a timeout. The outer wrapper's bounded waits can report unresolved state, but cannot make that nested process or its descendants disappear if they remain blocked in uninterruptible I/O.

The outer failure marker is not yet a closed accounting record. At `metered_joint_entry.py:158-163` it has attempt, technical-stop status, error, reaped-child CPU delta, self CPU snapshot, retry flag, and `accounting_complete=false`; it omits elapsed wall, child return/timeout outcome, cleanup result/error, `final_resource_pass=false`, final-settlement readback state, and registration terminal state. The reaped-child delta is only a lower bound if any owned descendant remains unreaped. In addition, the inner `_record_failure_settlement()` sets `final_resource_pass=false`, but the outer marker is the one that explicitly says `accounting_complete=false`.

Minimum fail-closed closure for this path:

1. Put a finite wait deadline after `SIGKILL`, then record whether the child was reaped. Preserve any `reap_owned_children()` exception and unresolved PID list instead of swallowing it. If either wait or reap is unresolved, return a technical stop with `accounting_complete=false`; do not wait without a bound and do not represent the attempt as settled.
2. Add `final_resource_pass=false`, elapsed wall, child return code or timeout, cleanup status/error, registration-terminal status, and whether a readable inner final settlement was available. Name the CPU that is known as `reaped_child_cpu_delta_lower_bound_seconds`; do not label it the full lifetime total if cleanup is unresolved. If the artifact schema requires a total/stage number, leave it null/unknown rather than synthesizing one.
3. Keep stage attribution incomplete on this path. An exception-time total difference cannot establish which stage or finalization operation consumed CPU. Only import per-stage data from a readable, identity-bound inner settlement as nested diagnostics; do not turn it into complete outer settlement while cleanup is unresolved.
4. To reliably close the server registration after timeout, the outer process must have a durable, unambiguous job identity before it can be needed. The robust minimal design is for the outer owner to create/own terminal registration, or to resolve the unique frozen attempt through a ledger API and append/verify exactly one terminal event. A child-written job-id sidecar narrows the gap but leaves a crash window between registration append and sidecar write. If the outer cannot resolve and verify the terminal event, record `registration_terminal_status="unknown"` and keep the overall result incomplete.

These fields make an incomplete failure diagnosable; they do not manufacture a complete total when a killed child or descendant cannot be reaped. If finite cleanup and terminal registration cannot be verified, that remains a blocker to any claim of complete exception-path settlement.

There is also a diagnostic accounting limitation in `joint_remote_native.py:43-64`: `_record_failure_settlement()` accepts `child_cpu_start` but reports all current `RUSAGE_CHILDREN` CPU without subtracting that baseline. Since it also marks `final_resource_pass=false`, this cannot produce a passing result, but the failure-side child CPU field can include pre-existing waited-child CPU and should not be interpreted as a precise per-attempt delta.

## Attribution and Wrapper Reserves

CPU differences are useful for scope reconciliation, not retrospective per-operation attribution. `joint_remote_native.py:319-345` records the inclusive waited-child total, an inner launcher snapshot, and `individual_tail_operation_cpu="not_measured"`; `cpu_scope_contract.py:241-247` explicitly defines the post-snapshot-to-reap tail as an inclusive settlement interval with no operation-level measurements. The retained historical `0.274925`-second discrepancy is explicitly marked as not retrospectively identifiable without preserved boundaries in `cpu-accounting-contract.json`. It must remain an unattributed delta; source snapshots do not establish that it came from any one fsync, registration append, export, or shutdown action.

The outer `launch_joint_once.py:212-232` checks controller CPU plus a two-second closing allowance, charges the full existing controller reserve, and adds five seconds to wall time. It labels closing cost as individually unmeasured. Those allowances are conservative accounting charges, not active limits: no controller `RLIMIT_CPU` or close deadline is installed. The local `windows-final-settlement.json` uses `Path.write_text()` after the resource decision, then JSON is printed and `client.close()` runs in `finally`; these close actions are not sampled and rechecked afterward. The five-second reserve cannot guarantee the file write or connection close completes in five seconds, and this file write is not an fsync-backed durable replacement. Therefore describe the wrapper close as reserve-charged/upper-bounded under the declared assumption, not measured or guaranteed durable.

## Review Disposition

Supported claim: on the normal, successful Linux path, waited lifetime plus disjoint parent self CPU can close the inner snapshot gap, including short-lived waited children and exit-tail CPU; nested snapshots are not double charged.

Blocked claim: this source does not establish kernel-hard CPU enforcement, bounded completion of every exception/timeout closeout, guaranteed persistence of both terminal registration and final settlement, or operation-level attribution of historical CPU deltas. Existing tests demonstrate accounting math and one real normal-path tail, but do not exercise outer `metered_joint_entry.main()` timeout/exception behavior, D-state I/O, interrupted fsync, or server registration persistence. No formal attempt, SSH call, or model/environment execution is claimed by this review.
